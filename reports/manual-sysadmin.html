System Overview

What the Smart Metering Portal does and how it fits in the HWA ecosystem

The Hargeisa Water Agency Smart Metering Portal (internally referred to as the Nobleus Portal) is the central digital operations platform for managing IoT-based smart water meters deployed across Hargeisa. It ingests live telemetry from the ThingsBoard IoT platform, stores readings locally in a MySQL database hosted on AWS EC2, and synchronises billing data to the HWA Core Billing system running on-premise via a secured REST API.

The system follows a hub-and-spoke integration model: all field devices report to ThingsBoard, which pushes webhook payloads to the portal. The portal normalises, validates, and enriches the data before forwarding relevant billing entries to the Core Billing API at reading.hargeisawatertech.com. A FortiGate firewall VIP at 102.218.58.66 provides network-level separation between the AWS environment and the on-premise HWA LAN.

Environment Variables (.env)

Complete reference for all application configuration keys

All environment-specific configuration is managed through a .env file in the application root (/var/www/nobleus-portal/.env). This file is loaded at bootstrap by the Yii 2 application. It is never committed to Git — the repository contains a .env.example template only.

🚫
Security Critical Never commit .env to any Git repository. The file contains database credentials, API tokens, and JWT secrets. Set file permissions to 640 and owner to www-data:www-data. Rotate all tokens at least every 6 months as per the security policy.

Apache Virtual Hosts

Virtual host configuration, SSL setup, and catch-all protection

The portal uses Apache 2.4 with multiple named virtual hosts to serve different sub-domains from the same EC2 instance. All virtual host configuration files reside in /etc/apache2/sites-available/ and are symlinked via a2ensite.

Sample Portal Virtual Host (HTTP → HTTPS redirect)
/etc/apache2/sites-available/portal.conf 
<VirtualHost *:80>
    ServerName  portal.hargeisawatertech.com
    ServerAlias www.portal.hargeisawatertech.com
    # Redirect all HTTP to HTTPS (Certbot manages this block)
    RewriteEngine On
    RewriteRule ^ https://%{HTTP_HOST}%{REQUEST_URI} [L,R=301]
</VirtualHost>

<VirtualHost *:443>
    ServerName   portal.hargeisawatertech.com
    DocumentRoot /var/www/nobleus-portal/web

    <Directory /var/www/nobleus-portal/web>
        Options         -Indexes +FollowSymLinks
        AllowOverride   All
        Require         all granted
    </Directory>

    # SSL — managed by Certbot
    SSLEngine             on
    SSLCertificateFile    /etc/letsencrypt/live/portal.hargeisawatertech.com/fullchain.pem
    SSLCertificateKeyFile /etc/letsencrypt/live/portal.hargeisawatertech.com/privkey.pem
    Include               /etc/letsencrypt/options-ssl-apache.conf

    # Security headers
    Header always set Strict-Transport-Security "max-age=31536000; includeSubDomains"
    Header always set X-Content-Type-Options     "nosniff"
    Header always set X-Frame-Options            "SAMEORIGIN"

    ErrorLog  ${APACHE_LOG_DIR}/portal-error.log
    CustomLog ${APACHE_LOG_DIR}/portal-access.log combined
</VirtualHost>

🛡️
Catch-All Virtual Host — Always Keep Enabled The 000-catch-all.conf virtual host intercepts any HTTP request that does not match a named ServerName. This prevents direct access to the application via the raw EC2 IP address (e.g. http://54.x.x.x/), which could bypass security headers and expose internal details. It returns a generic 403 Forbidden for all bare-IP or unrecognised hostname requests.

Billing Date Policy — The 28th Rule

How the system assigns official billing dates to meter readings
📅
Company Policy — Billing Date Standardisation By HWA billing policy, all meter readings use the 28th of the reading's billing month as the official billing date, regardless of when within the month the reading was actually recorded or processed. This ensures consistent billing cycles and simplifies reconciliation with the HWA Core Billing system.
Implementation in Code

The 28th-of-month rule is implemented in two places in the application:

Bulk Action (actionPostToBilling): When posting a batch of readings for a given month, the billing date is computed as:

PHP — bulk billing date assignment 
// $month is in 'YYYY-MM' format (e.g. '2026-06')
// Always append '-28' to get the standardised billing date
$billingDate = $month . '-28';

// Example: $month = '2026-06'  →  $billingDate = '2026-06-28'
$payload = [
    'accountNo'   => $reading->account_no,
    'readingDate' => $billingDate,
    'reading'     => $reading->value_m3,
];

Single Import (actionImport): When importing individual readings, the billing date is derived from the reading's own timestamp, replacing the day component with 28:

PHP — single reading billing date 
// Derive billing date: take reading's year-month, fix day to 28
$billingDate = date('Y-m', $reading->ts) . '-28';

// If reading was on 2026-07-15 09:30:00 UTC,
// billingDate becomes '2026-07-28'
Billing Date Behaviour Matrix
ScenarioReading DateBilling Date AssignedDescription / Notes FieldOutcome
Reading on the 28th 2026-06-28 2026-06-28 No special note appended Standard
Reading on another day 2026-06-15 2026-06-28 Description appended: "Reading date adjusted to billing date 28th" Adjusted
Reading on last day of month 2026-06-30 2026-06-28 Description appended noting original reading date Adjusted
No reading for month — — Entry skipped entirely; no billing record pushed Skipped
Zero reading received Any date Month-28 Zero-consumption record pushed; flagged in audit log Review
ℹ️
February Handling February always has at least 28 days (1–28), so the 28th always exists and is valid for any year. No special leap-year logic is required for billing date generation.

Billing Audit Log Query — Failed Pushes
SQL — billing audit investigation 
-- Recent billing push failures with full response details
SELECT
    bal.id           AS audit_id,
    bl.meter_id,
    bl.billing_month,
    bl.billing_date,
    bal.attempted_at,
    bal.http_status,
    LEFT(bal.response_body, 200) AS response_snippet,
    bal.success
FROM       billing_audit_logs bal
INNER JOIN billing_ledger bl ON bl.id = bal.ledger_id
WHERE  bal.success = 0
  AND  bal.attempted_at >= NOW() - INTERVAL 7 DAY
ORDER BY  bal.attempted_at DESC;

Troubleshooting Reference

Common issues, their causes, and step-by-step remediation

The table below covers the most frequently encountered operational issues. For each issue, the most likely cause is listed alongside the diagnostic command and recommended fix. Always check the Yii app log first (runtime/logs/app.log) before escalating.

SymptomLikely CauseDiagnostic CommandResolution
Billing push status shows "failed" in billing_ledger Expired CORE_API_TOKEN (JWT), network timeout to FortiGate, or duplicate entry rejected by Core API tail -100 runtime/logs/app.log | grep FAILED; check billing_audit_logs.response_body If JWT expired: generate a new token from HWA IT, update .env, reload Apache. If duplicate: mark record as resolved in billing_ledger. If network: check AWS security group outbound 443 and 5432.
Apache SSL certificate error — browsers show "cert expired" warning Certbot auto-renewal cron failed (e.g., port 80 blocked during ACME challenge, cron disabled) sudo certbot certificates; sudo journalctl -u certbot; sudo crontab -l Ensure port 80 inbound is open in AWS security group for ACME HTTP-01 challenge. Run sudo certbot renew --force-renewal. Verify /etc/cron.d/certbot exists and cron daemon is running.
504 Gateway Timeout on bulk billing post action Large number of records being pushed in a single HTTP request exceeds the Apache / PHP max execution time; or slow response from Core Billing API Check portal-error.log for "Timeout" or "script timed out"; check Core API latency from EC2 with curl -w "%{time_total}" -o /dev/null -s https://reading.hargeisawatertech.com/health Increase max_execution_time in /etc/php/8.3/apache2/php.ini (e.g. to 300). Set TimeOut 300 in the Apache vhost. Alternatively, run bulk operations from CLI: php yii billing/post-to-billing --month=2026-06.
Meter readings not appearing in portal after ThingsBoard sends webhook Invalid or missing TB_WEBHOOK_TOKEN causing 401 rejection; wrong TB_TELEMETRY_KEY so the payload key is not parsed; or webhook URL pointing to wrong endpoint grep "webhook" runtime/logs/app.log | tail -20; also check ThingsBoard rule engine logs for delivery failures Verify the webhook URL in ThingsBoard points to https://portal.hargeisawatertech.com/api/webhook/thingsboard. Confirm TB_WEBHOOK_TOKEN in .env matches the token set in the TB rule engine. Verify TB_TELEMETRY_KEY matches the exact JSON key name in telemetry payloads.
Readings appear as zero for multiple meters across a period Meter device offline or not transmitting; ThingsBoard receiving zero telemetry; TB_TELEMETRY_KEY misconfigured returning 0 instead of null Log into ThingsBoard UI → Latest Telemetry for the affected devices. Cross-reference with SELECT meter_id, AVG(value_m3) FROM meter_reading_raw WHERE received_at > NOW()-INTERVAL 7 DAY GROUP BY meter_id; If ThingsBoard shows non-zero values: check TB_TELEMETRY_KEY in .env. If ThingsBoard also shows zero: escalate to field team for physical meter inspection. Ensure the meter device has network connectivity and is reporting to TB successfully.
billing_audit_logs table is empty after bulk post action No billing entries exist in billing_ledger for the selected month; OR the bulk post action did not run (user cancelled, permission error); OR audit log insert is failing silently SELECT COUNT(*) FROM billing_ledger WHERE billing_month = '2026-06';; check runtime/logs/app.log for "post-to-billing" action completion message If ledger count is zero: readings were not processed for that month — check ThingsBoard webhook delivery for that month. If ledger exists but audit log is empty: check MySQL user permissions on billing_audit_logs table (SHOW GRANTS FOR 'nobleus_app'@'localhost';) and confirm INSERT privilege is granted.

Security Checklist

Mandatory and recommended security controls for production operation

The following checklist must be reviewed at initial deployment and re-verified at least every six months. Items marked with a red badge represent critical controls — any failure immediately increases attack surface or data exposure risk.

Token & Credential Management
  • ✅
    Rotate CORE_API_TOKEN (JWT) every 6 months. Coordinate with HWA IT to generate a new token from the Core Billing API. Update .env and reload Apache. Log the rotation date in the ops log. Critical
  • ✅
    Rotate TB_WEBHOOK_TOKEN every 6 months. Generate a new strong random token (32+ chars), update in both ThingsBoard rule engine and the portal .env, then reload Apache. Critical
  • ✅
    Never commit .env to any Git repository. Verify .env is listed in .gitignore. Periodically run git log --all --full-history -- .env to confirm it has never been committed. Critical
  • ✅
    Set .env file permissions to 640, owned by www-data:www-data. Command: sudo chmod 640 /var/www/nobleus-portal/.env && sudo chown www-data:www-data /var/www/nobleus-portal/.env
Application Configuration
  • ✅
    Ensure YII_DEBUG=false in production. Debug mode exposes full stack traces, configuration details, and SQL queries in the browser — a severe information disclosure risk. Critical
  • ✅
    Ensure YII_ENV=prod in production. This disables development-only behaviours, profiling panels, and Gii code generation scaffolding.
  • ✅
    Ensure CORE_API_INSECURE_SSL=0 (or unset) in production. Setting this to 1 disables TLS verification on all Core Billing API calls, exposing all JWT tokens to MITM attacks. Critical
SSL & Transport Security
  • ✅
    SSL auto-renewal cron is active and tested. Run sudo certbot renew --dry-run monthly to verify ACME renewal works. Verify /etc/cron.d/certbot exists.
  • ✅
    HSTS header is set on all SSL virtual hosts. Confirm Strict-Transport-Security header appears in responses: curl -I https://portal.hargeisawatertech.com | grep Strict
  • ✅
    HTTP-to-HTTPS redirect is enforced on all virtual hosts. Test: curl -I http://portal.hargeisawatertech.com must return 301 Moved Permanently pointing to HTTPS.
Database Security
  • ✅
    MySQL user nobleus_app is restricted to localhost connections only. Verify: SELECT host, user FROM mysql.user WHERE user='nobleus_app'; — result must show 127.0.0.1 or localhost only.
  • ✅
    MySQL is bound to 127.0.0.1 only (not 0.0.0.0). Check /etc/mysql/mysql.conf.d/mysqld.cnf — bind-address = 127.0.0.1 must be set. Port 3306 must not appear in EC2 security group inbound rules.
AWS & Network Security
  • ✅
    Catch-all virtual host (000-catch-all.conf) is always enabled. This prevents bare-IP access. Test: curl -I http://<EC2-IP>/ must return 403, not a portal page.
  • ✅
    AWS EC2 security group inbound rules: only ports 80 (HTTP) and 443 (HTTPS) open to 0.0.0.0/0. SSH (port 22) must be restricted to the administrator's office IP range, never 0.0.0.0/0. Critical
  • ✅
    AWS EC2 security group outbound rules: allow TCP 443 to 0.0.0.0/0 and TCP 5432 to 102.218.58.66/32. Restrict all other outbound traffic where possible.
  • ✅
    AWS EC2 instance is in a VPC with a defined network ACL. Ensure the NACL does not inadvertently expose internal services to the internet.
Operational Hygiene
  • ✅
    Ubuntu unattended security updates are enabled. Verify: sudo dpkg -l unattended-upgrades — package must be installed and configured. Check /etc/apt/apt.conf.d/50unattended-upgrades.
  • ✅
    EBS volume snapshots are scheduled (at minimum weekly). Configure AWS Backup or DLM (Data Lifecycle Manager) policy for the root EBS volume. Retain at least 4 snapshots.
  • ✅
    MySQL backups are performed daily. Example cron: 0 2 * * * mysqldump -u root nobleus_db | gzip > /var/backups/nobleus-$(date +\%F).sql.gz. Verify backups can be restored.
